CSS Variables

The entire look of molique — colors, spacing, typography, dark mode — rests on CSS variables. You never need to override a rule to change the theme: just swap the values.

1. How it works

A CSS variable is a named box for a value. The framework never hardcodes a color — it always reaches for a variable. When you swap its contents, the change propagates instantly through every component that uses it.

Variables inherit down the DOM tree — exactly like text color. That's why the scope of a change depends entirely on which element you declare it on. It's also why PurgeCSS must never remove them — see pitfall #3.

Category How many Declared where Who sets it
Theme variables 89 :root in _root.scss You — globally, once per project.
Component variables 60 The component's own file The framework. Some can be overridden in markup.
Markup inputs 6 Nowhere — they're only read You, exclusively. Without them the component has no data to draw from.

2. How to override a value

Three scopes, from widest to narrowest. All of them work without !important — you're not fighting specificity, just supplying a different value.

Scope 1 The whole project

Your own stylesheet loaded after molique. This is the correct way to theme your brand. 

<link rel="stylesheet" href="css/molique-style.css">
<link rel="stylesheet" href="css/my-theme.css">   <!-- after molique -->
/* my-theme.css */
:root {
  --primary: #7C3AED;
  --primary-hover: #6D28D9;
  --primary-rgb: 124, 58, 237;   /* MUST match --primary */

  --border-radius: 4px;          /* sharper interface */
  --spacing-unit: 6px;           /* tighter rhythm across the framework */
}

Scope 2 One section

A declaration on a container covers everything inside it. Useful when one section needs a different accent than the rest of the page. 

<section class="container p-5" style="--primary: #059669;">
  <!-- every .btn-primary and .text-primary in here is green -->
  <button class="btn-primary">Save</button>
</section>

Scope 3 A single element

This is how you pass data from the backend — progress, a rating, a stock level. The numeric value rides in a variable, not in a class, because classes must never be concatenated dynamically. 

<div class="star-rating" style="--rating: 4.5;"></div>
<div class="stock-bar stock-bar-warning" style="--stock-filled: 2;"></div>
<div class="chart-radial" style="--val: 75%;"></div>

3. Dark mode

The dark theme is nothing but a different set of values — zero extra rules, zero duplicated components. The data-theme="dark" attribute on <html> swaps 31 of the 89 theme variables.

That's why, when you add your own color variable, you must declare it in both blocks. A variable declared only in :root stays the same in dark mode and will most likely disappear against the dark background. 

:root {
  --brand-accent: #B45309;
}

[data-theme="dark"] {
  --brand-accent: #FBBF24;   /* lighter, so it stays readable on dark */
}
Where the system theme comes from

Both blocks also declare color-scheme. That's what makes native controls — scrollbars, the calendar in input[type="date"], the <dialog> backdrop — follow the theme. Without this declaration, modal headings can end up black on a dark card.

4. Four pitfalls

Every one of these has already cost someone an afternoon. They all boil down to the same thing: a variable doesn't say what it is — you have to know.

1 --dark doesn't mean "dark"

In the light theme --dark is #1E293B (graphite), but in dark mode it flips to #F8FAFC (white). It's not "the dark color" — it's the color that contrasts with the background. Likewise --light becomes dark in dark mode.

The consequence: used on an element sitting on a photo — whose background doesn't change with the theme — it gives white text on a white background. 

/* WRONG - on a photo the text vanishes in dark mode */
.photo-caption { color: var(--dark); }

/* RIGHT - a literal value, independent of the theme */
.photo-caption { color: #1E293B; }
2 --x and --x-rgb are not the same thing

--primary is a ready-made color. --primary-rgb is just the channels (2, 132, 199) — without it you can't build transparency. It only works inside rgba().

Used anywhere else it's not a valid color, so the browser discards the entire declaration — silently, with no console error. 

/* WRONG - "2, 132, 199" is not a color, the declaration is dropped */
.card { border-color: var(--primary-rgb); }

/* RIGHT */
.card { border-color: var(--primary); }
.card { background: rgba(var(--primary-rgb), 0.1); }

When you change --primary in your theme, always change --primary-rgb too. Letting the pair drift apart gives you transparencies in the old color.

3 PurgeCSS with variables: true wipes out the theme

This option removes CSS variables PurgeCSS couldn't find in your files. The problem is that molique's variables are used inside the framework's own rules, not in your HTML — so the tool considers them dead and strips them. The result: a page with no colors and no spacing. 

// purgecss.config.js
module.exports = {
  variables: false,   // LEAVE false - the whole theme rests on variables
};

Details and a ready-made config: PurgeCSS & safelist.

4 The admin sidebar is always dark

--sidebar-bg deliberately has no dark-mode counterpart — the sidebar looks the same in both themes. That's why its light accents must be literal values.

Using --light-rgb there looks correct in the light theme, but in dark mode that variable flips to dark — and the text and highlights disappear against the sidebar's dark background. That's what the separate --sidebar-highlight-rgb is for. 

/* WRONG - the hover will disappear in dark mode */
.admin-nav-link:hover { background: rgba(var(--light-rgb), 0.1); }

/* RIGHT - an accent independent of the theme */
.admin-nav-link:hover { background: rgba(var(--sidebar-highlight-rgb), 0.1); }

5. Theme variables 89

Declared in :root. The Dark mode column shows the value once the dark theme is on — no change means the variable is shared by both themes. The Used in column points to the Sass modules that use it.

This reference table is auto-generated from the Sass source and is currently available in Polish only. Variable names (--primary, --spacing-unit…) and values need no translation either way.

6. Component variables 60

Declared inside a specific component, so they only work within it. Two kinds:

  • markup — meant to be overridden by you, usually via style="--x: …".
  • internal — the framework computes these itself. Listed here because they're visible in DevTools, and it's worth knowing this isn't where your changes belong.

7. Markup inputs 6

Variables the framework never declares — it only reads them. This is the interface for passing data from the backend. If the When not set column shows required, leaving it out means the component won't render correctly.
