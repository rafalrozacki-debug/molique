# Molique JIT - Data Structures (actual state after Phases 1-5)

> The original version of this document described `MoliqueAstNode` (Utility/
> Component/State) built ON THE FLY by a "Rule Parser" from class names and
> mathematical dictionaries. This engine was never built in that form -
> see `jit-spec.md` section 0 for why. There is no longer a
> "rule parser" or AST objects built at runtime: the data is
> PRE-COMPILED (by real Sass, in this repository) and
> saved as JSON, and the engine in the `molique-jit` package does nothing but
> key-based lookups. This document describes the actual shape of the data -
> the source of truth is `tools/jit/package/src/types.ts`.

## 1. Utility class dictionary (`utilities.json`)

Generated by `tools/gen-jit-utilities.js` from the already compiled
`dist/chunks/molique-utilities.css` / `molique-utilities-extended.css`.

```typescript
export interface UtilityRule {
  /** Full selector text, e.g. ".text-hover-primary:hover". */
  selector: string;
  /**
   * Conditions wrapping the rule, from outermost to innermost, e.g.
   * ["@media (min-width: 768px)", "@supports (animation-timeline: view())"].
   * Empty array = no condition.
   */
  wrappers: string[];
  /** CSS declarations (without selector and braces), e.g. "color:var(--primary) !important". */
  css: string;
  /** Name of the source chunk, e.g. "molique-utilities-extended.css" (opt-in module). */
  source: string;
}

/** CSS fragment with no class in the selector (e.g. @keyframes, @property) - always included. */
export interface AlwaysIncludeEntry {
  raw: string;
  source: string;
}

export interface UtilitiesDictionary {
  generated: string;
  sources: string[];
  classCount: number;
  ruleCount: number;
  alwaysIncludeCount: number;
  /** Class name -> LIST of rules (a single class can have more than one rule, e.g. base + :hover). */
  classes: Record<string, UtilityRule[]>;
  alwaysInclude: AlwaysIncludeEntry[];
}
```

**Why `wrappers` is an array, not a single `mediaQuery: string`
(as in the original version of this document):** a real case was found in
`_animations.scss` - `.scroll-reveal` is nested simultaneously inside
`@media (min-width: 768px)` AND `@supports (animation-timeline: view())`.
A single `mediaQuery` field would have lost this second condition.

**Why `classes[name]` is an array, not a single object:** the same
selector is sometimes defined more than once in the same SCSS file with different
declarations (e.g. `.hover-opacity-100` in `_helpers.scss` - once without
`!important`, once with, the second one wins in the cascade). The engine includes ALL
variants verbatim, exactly as a full Sass build would.

**Owner rule for compound selectors** (e.g.
`[data-theme="dark"] .bg-glass`, `.stacking-container-snap .section-stacked`):
the LAST class in the selector owns the entry. This is a safe
simplification in one direction only: in the worst case a compound rule will be
included without its use of the parent class (a harmless, "dead" CSS fragment -
the descendant selector won't match any element without the parent in the DOM anyway),
never the other way around.

## 2. Component index (`class-index.json`)

Generated by an extended section in `tools/gen-chunks.js`.

```typescript
export interface ClassIndex {
  generated: string;
  /** CSS class -> component chunk ID, e.g. "card" -> "cards". */
  classes: Record<string, string>;
}
```

It covers `css/scss/components/*.scss` AND three core chunks which, despite
their "core" category, behave like components from the JIT's perspective -
included based on the USE of a specific class, not merely the presence of the
framework: `buttons` (`.btn-primary` etc.), `grid` (`.col-span-*`,
`.grid-cols-*`, `.offset-*`, `.bento-*`), `layout` (`.d-flex`, `.gap-*`,
`.align-items-*`, `.w-*` etc.). Found and fixed in Phase 5 -
the original version covered ONLY the `components/` folder, which meant e.g.
`.btn-primary` didn't resolve at all.

When a matched token is a key in this map, the engine includes the ENTIRE
compiled `dist/chunks/molique-<id>.css` file verbatim - never
partially (components have selectors that depend on DOM structure, which
a plain class scan cannot safely reconstruct in fragments).

## 3. Always-included data (outside the maps)

- `molique-root.css` (`:root` variables + `[data-theme="dark"]`) and
  `molique-base.css` (reset, base typography, `.container`/
  `.container-fluid`) - both marked `mandatory: true` in
  `tools/gen-chunks.js`, ALWAYS included, regardless of which
  classes were scanned.
- `safelist.json` (`tools/gen-jit-package-data.js`, tier
  `runtime.standard` from `purgecss.safelist.cjs`) - classes created/
  toggled by molique's OWN JS (toasts, carousel, lightbox,
  sidebar) - treated as always present in the effective set of tokens
  to match, regardless of what the scanner actually found.

## 4. Order in the output CSS

The emitter (`tools/jit/package/src/emitter.ts`) assembles the final file in a fixed
order - see `jit-spec.md` section 1.4. There is no "AST sorting" stage
here like in the original plan - the order results directly from the sequence
in which the emitter appends the ready-made fragments (root+base, then
components, then utilities grouped by `wrappers`, and finally
`alwaysInclude`).
